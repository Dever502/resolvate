# Техническое устройство

Архитектура, данные и гарантии системы. Установка и обслуживание описаны в
[OPERATIONS.md](OPERATIONS.md).

## Назначение и границы

Установка обслуживает несколько проектов. `installation.py` предоставляет одну Web-панель,
один HTTP listener и общий ограниченный пул PostgreSQL; у каждого активного проекта свой бот,
набор сервисов, очереди и настройки. Аккаунты общие, членство и администрирование проектные.
На бизнес-таблицах обязательный `project_id`, PostgreSQL FORCE RLS и проверки межпроектных ссылок.
Контекст устанавливается локально на каждую транзакцию и не остаётся в пуле соединений.
Без контекста бизнес-данные недоступны. Runtime-роль не должна владеть таблицами, иметь SUPERUSER
или BYPASSRLS. Владелец сервера и БД остаётся доверенным лицом, не объектом этой изоляции.
Медиа, кеши и runtime-сервисы не разделяются между проектами. Изменение настроек перезапускает
только соответствующий проект с корректным завершением старых обработчиков.
Подробности настройки и границ Telegram-доступа — [CONSOLE.md](CONSOLE.md).

Система связывает Telegram-чат или backend сайта с темой закрытой Telegram Forum-группы. Web API,
Operator API, Remnawave и notification webhook включаются независимо. Поддерживается один процесс;
единственная поддерживаемая база — PostgreSQL 16.

```text
Telegram updates ──> Telegram adapter ──┐
Web Support API ────> Web adapter ──────┼──> application services ──> SQL database
Operator REST API ──────────────────────┘              │
                                                      ├──> Remnawave API
                                                      └──> durable outbox
                                                               │
                                                        delivery workers
                                                          │         │
                                                     Telegram   webhook
```

Transport-слой не содержит бизнес-правил, а прикладные сервисы не зависят от aiogram или
FastAPI. Основные модули:

| Область | Модули |
| --- | --- |
| Telegram и тикеты | `telegram_*`, `ticket_*`, `services.py`, `quick_replies.py` |
| доставка | `outbox_repository.py`, `delivery.py`, `notification_webhook.py` |
| Remnawave | `panel*`, `remnawave.py` |
| API и runtime | `api*`, `web_api*`, `__main__.py`, `runtime_health.py` |
| данные | `models.py`, `database.py`, Alembic migrations |

Границы проверяются architecture-тестами.

### Производительность горячих путей

- Проверки межпроектных ссылок сохраняют тип индексированного ID: приводится параметр,
  а не колонка. Триггеры выполняются при вставке и изменении ссылки или `project_id`,
  но не на каждом обновлении времени активности. FORCE RLS остаётся обязательным.
- Активные и архивные диалоги имеют отдельные индексы по проекту, времени активности и ID;
  статистика использует индекс сообщений по проекту/времени и один групповой запрос
  вместо трёх повторных подсчётов входящих сообщений. Миграция `0008_backend_hot_paths`
  добавляет индексы и обновляет триггеры существующих установок без изменения данных.
- Непрочитанные считаются по частичному покрывающему индексу входящих нескрытых сообщений
  (`0009_console_read_paths`), без чтения их содержимого; отметка прочтения присоединяется
  один раз на тикет и остаётся персональной для оператора. Индекс требует дополнительного
  места и обслуживания при записи, но сокращает чтение длинных переписок. Карточка тикета,
  клиент и его идентификаторы загружаются одним запросом с сохранением проектной изоляции.
  Сначала выбираются ID текущей страницы с её фильтрами и порядком, затем считаются
  непрочитанные и выбираются превью: пропущенные через OFFSET диалоги не читают историю.
- При обновлении нескольких страниц списка Web передаёт известные ревизии только для
  соответствующей предыдущей страницы, а не всего списка для каждой страницы. Переместившиеся
  между страницами диалоги возвращаются полностью; формат API и последовательный опрос сохранены.
- Загрузка, проверка и синхронизация временного файла не удерживают общий замок медиа.
  Замок берётся перед публикацией и удерживается до завершения транзакции вызывающего
  сервиса, включая сохранение ссылки в БД. Ограничение параллельных проверок, валидация
  форматов и защита от удаления/сжатия используемого файла сохранены. При отмене запроса
  выполняющаяся файловая операция завершается до освобождения замка и временного файла.
- Синхронизация истории выбирает в БД только самую раннюю известную позицию вместо
  повторной загрузки всей истории; для статусов доставки не читаются тела заданий
  и сохранённых команд отправки — из JSONB выбираются только ID доставок.
  Проверка исчезнувших сообщений использует множество, а не повторный обход списка.
  Формат API и логика восстановления непрерывного окна истории не изменены.
- После коммита изменений outbox текущий runtime пробуждает delivery worker локальным
  событием. Событие — только подсказка: готовность, порядок и владение заданиями
  по-прежнему проверяет PostgreSQL. Секундный опрос сохранён для других подключений,
  отложенных повторов и восстановления; паузы после ошибок не сокращаются.
- Антиспам очищает только истёкшую часть упорядоченного реестра клиентов. Лимиты,
  окна, уведомления и ограничение числа ключей не изменены.
- Очистка очередей не перезаписывает уже пустые payload неудачных заданий; подсчёт
  занятого медиа места переиспользует метаданные обхода, не следует симлинкам.
  Для сжатия выбираются только два кандидата за тик, с сохранением курсора обхода;
  остальные операции очистки сохраняют прежний размер пакета.

## Ротация топиков: разрабатываемый механизм

Журнал `topic_archives` / `transcript_messages` отделяет физический топик от постоянного тикета.
Worker заменяет переполненный закрытый топик либо освобождает место, удаляя закрытый топик
без немедленного создания нового. Подготовка отменяется при возобновлении сессии до переключения.
После начала переключения сообщения остаются в PostgreSQL-очереди до готовности нового топика.

Ingress, delivery и reconciliation используют общую короткую блокировку БД. Сетевые вызовы
под ней не выполняются. После замены поздние ответы оператора привязываются к текущему тикету,
а в новом топике отображаются отдельной копией с автором; это не повторная отправка клиенту.
Для удалённого источника предусмотрено восстановление поддерживаемого сообщения из сохранённого
снимка и Telegram file_id. Оно не является независимым файловым архивом.

Перед удалением проверяются журнал, вложения, незавершённые доставки, отсутствие новых записей
и сохранение всей полученной после переключения пачки Telegram updates. Состояние переезда
переживает рестарт. Неоднозначное создание нового топика не повторяется автоматически: источник
сохраняется, очередь может продолжить работу через него, а результат создания требует проверки.
Bot API не предоставляет общей транзакции с БД, идемпотентного создания топика или гарантии
exactly-once отправки. Закрытие топика также не заменяет управление правами администраторов.

Обычный облачный Bot API остаётся единственным режимом. Вложения больше 20 * 1024 * 1024 байт
получают статус `skipped_cloud_limit`; метаданные сохраняются. Ошибки сохранения остальных файлов
не превращаются в пропуск. Старые топики без полного журнала автоматически не удаляются.

Интеграция AI и эксплуатационная проверка Telegram дорабатываются отдельно.
Текущий экспорт медиа обслуживает Web-медиа, не новый архив Telegram-вложений.

### Обслуживание архивного хранилища

При запуске приложения также запускается `ArchiveMaintenance`. Он проверяет место в фоне,
удаляет тела архивных сообщений по `ARCHIVE_RETENTION_DAYS` (60 дней), а сохранённые файлы —
по `ARCHIVE_MEDIA_RETENTION_DAYS` (30 дней). Небольшая запись о бывшем топике остаётся для
маршрутизации и признака прошлых обращений. Отсчёт идёт от `archived_at`, не от скачивания или
сжатия. Проверки файлов выполняются каждый час, переписки — ежедневно; большие очереди
обрабатываются порциями. При рестарте проверка начинается снова, сроки не продлеваются.

После `ARCHIVE_MEDIA_COMPRESS_AFTER_DAYS` (14 дней) фотографии могут заменяться меньшим WebP
без потери пикселей и уменьшения разрешения. Видео MP4/MOV с одним видеопотоком и не более
одного аудиопотока сжимаются H.264, CRF 23, с сохранением аудио. Лимиты видео: 10 минут,
8 294 400 пикселей на кадр. Документы, анимации и неподходящие форматы не преобразуются.
Обработка идёт последовательно отдельными процессами: один поток кодирования, пониженный
приоритет, до 768 МиБ адресного пространства и 120 секунд на файл. Результат принимается
только после проверок и при уменьшении размера; ошибки оставляют оригинал. Для установки
без Docker нужен FFmpeg/ffprobe в системном PATH; отсутствие не блокирует остальную очистку.

Бюджет `MEDIA_BUDGET_BYTES` (20 ГиБ) учитывает файлы в `web-media` и `transcript-media`, включая
временные и сжатые. При 80% фиксируется предупреждение, при 90% учащается очистка просроченного.
Превышение бюджета или нехватка свободного места разрешают досрочное удаление самых старых
подходящих архивных вложений. Если остаются только защищённые данные, бюджет может превышаться.
Общие файлы защищены всеми ссылками; активные топики, переезды и незавершённые доставки
препятствуют очистке. После удаления файла остаются метаданные и `deleted_at`.

`STORAGE_RESERVE_BYTES` (3 ГиБ) проверяется при резервировании места под скачивание и сжатие.
Очистка по свободному месту начинается заранее: дополнительно нужен запас под файл до 20 МиБ.
Web и Telegram используют общий резерв в одном процессе; Web API при отказе возвращает 503
с предложением повторить загрузку. Telegram-архивация откладывается. `ARCHIVE_BUDGET_BYTES`
(2 ГиБ) — предупредительный порог суммы размеров JSONB-полей архивных сообщений, не размер
PostgreSQL, индексов или WAL. Он не разрешает удалять тексты раньше срока. Диск отдельного
сервера PostgreSQL необходимо контролировать средствами его эксплуатации.

Обслуживание рассчитано на один процесс приложения. Между проходами предусмотрена пауза
60 секунд; длительная обработка медиа может увеличить интервал. Инциденты сохраняются
в `operational_notices` и отправляются в General группы `SUPPORT_GROUP_ID`.
Удаление в основном хранилище не удаляет копии из внешних резервных копий или Telegram.

### Системные уведомления в General

`GeneralNoticeWorker` отправляет эксплуатационные предупреждения без `message_thread_id`
и без привязки к чужому сообщению. Отдельный топик или получатель не создаются, `/start`
в личке не требуется. Неиспользуемая настройка `ROTATION_ADMIN_TELEGRAM_ID` удалена.

Сообщения касаются заполнения хранилища, ошибок архивации/переезда и досрочного удаления
архивных вложений. Для каждого типа есть фиксированный публично-безопасный текст: содержимое
переписки, произвольный текст из БД, пути, токены и тела исключений не пересылаются.
Обычная фоновая очистка по лимиту топиков не считается инцидентом и не публикуется.

Сохраняющиеся проблемы повторяются не чаще раза в час. Новое состояние или смена серьёзности
сообщаются отдельно; подтверждённое восстановление — один раз, только после отправленного
предупреждения. Разовые события, например досрочное удаление, группируются по типу в часовом
окне, без выдуманного сообщения о «восстановлении» удалённых данных.

Миграция `0003_notice_delivery` сохраняет состояние отправки. Сетевые вызовы не удерживают
транзакцию БД. При подтверждённом отказе Telegram повтор откладывается, при 429 учитывается
`retry_after`. После неизвестного результата отправки или рестарта в её середине выдерживается
часовой интервал: это предотвращает поток дублей, но доставка может задержаться; exactly-once
не гарантируется. Закрытый/скрытый General автоматически не открывается. Ошибки этого worker
не блокируют доставку сообщений клиентов и операторов.

## Тикеты и сообщения

Тикет находится в состоянии `provisioning`, `open` или `closed`, имеет канал `telegram|web`, а
`topic_id` уникален. Telegram и Web identities автоматически не объединяются. На одну Web identity
существует один постоянный тикет/topic. Новое сообщение открывает следующий close cycle, в котором
допустима одна оценка.

Папки панели хранятся в `ticket_folders` с проектной RLS и уникальным нормализованным
именем внутри проекта. `tickets.folder_id` допускает NULL; внешний ключ имеет `ON DELETE SET NULL`,
а project-reference trigger запрещает ссылку на папку чужого проекта. Миграция `0007_ticket_folders`
сохраняет существующую переписку и исходно оставляет её без папок.

Короткие изменения папок сериализуются transaction advisory lock внутри проекта. Перемещения
дополнительно блокируют строку тикета и проверяют `folder_revision`; переименование и удаление
проверяют ревизию папки. Устаревшая операция получает HTTP 409. Удаление папки и снятие назначений
с увеличением их ревизий выполняются одной транзакцией. Статус и `last_activity_at` не меняются.
Действия записываются в `access_audit`; сетевых вызовов под блокировкой нет. Все endpoints папок
доступны только участникам проекта, с обычными session/CSRF-проверками панели.

Создание Forum-темы защищено provisioning token. Неизвестный результат Telegram-вызова остаётся
для ручной проверки: автоматический повтор мог бы создать вторую тему.

Сообщение сначала фиксируется в `ticket_messages`, затем попадает в `delivery_outbox`:

```text
waiting_topic ──> pending ──> processing ──> delivered
                     ▲              │
                     └──── retry ────┘
                                    └────> failed
```

Гарантии доставки:

- запись сообщения до внешней отправки;
- FIFO внутри тикета и ограниченные повторы с backoff;
- возврат зависших `processing` заданий;
- восстановление удалённой темы и перенаправление незавершённых сообщений;
- общая блокировка тикета перед ingress и ответом оператора; legacy blocklist сохраняет
  совместимость Telegram-блокировки до создания тикета;
- дедупликация Telegram updates и API-мутаций;
- персональный admission limit: 8 сообщений за 5 секунд, 30 в минуту и 200 в час.

Ответ оператора Telegram доставляется из принятой записи `ticket_messages`, включая текст,
форматирование и Telegram file ID вложения, а не копированием изменяемого сообщения из группы.
Правка с действующим доступом обновляет принятую версию; правка после отзыва доступа — нет.
Журнал темы не используется как резервный источник операторского ответа. Это правило действует
и для ранее созданных заданий очереди; у старых записей без сохранённых entities текст отправляется
без форматирования. При отсутствии принятой записи доставка не подменяет её содержимым Telegram.

Стикеры Telegram сохраняются тем же project-scoped media storage: PNG/WebP до 512 KiB,
TGS до 64 KiB и WebM/VP9 без звука до 256 KiB (до 3 секунд). Отдельный режим валидатора
доступен только для Telegram sticker, не произвольных Web/API uploads. TGS разбирается
в ограниченном процессе: лимит распаковки 2 MiB, глубины/сложности и графа precomposition;
внешние ресурсы, expressions, текст/шрифты, эффекты и повторители не принимаются.
WebM проверяется на целостность контейнера, отсутствие вложенных файлов, кодек, размеры и FPS.
Оригиналы участвуют в дедупликации, backup и retention; повторное сжатие стикеров не выполняется.
TGS выдаётся авторизованному участнику как gzip JSON. Backend-приём, хранение и Telegram-доставка
сохранены; просмотр стикеров в новой Vue-панели ещё не реализован. Старый браузерный проигрыватель
удалён вместе с прежним фронтендом. CSP не ослаблена.

Уведомление операторам о спаме сохраняется как внутреннее сообщение и outbox-доставка
в одной транзакции, не попадает в клиентскую историю Web API. Для Telegram контрольное событие
идёт по той же durable очереди и ordering key, что и принятые сообщения клиента: создание
нового тикета успевает завершиться до записи предупреждения. Отклонённый текст не сохраняется.

Если запись входящего Telegram update в БД завершилась ошибкой, последовательный polling
ждёт успешного сохранения и не продвигает подтверждение этого update. Повторяется только запись
того же payload: квота клиента не списывается повторно. Пауза растёт от 1 до 5 секунд;
это также относится к внутреннему событию антиспама. Отмена при остановке оставляет
несохранённый update неподтверждённым. При длительном сбое действуют сроки хранения
неподтверждённых updates на стороне Telegram; бесконечное хранение не гарантируется.

Доставка — **at-least-once**. Telegram не поддерживает idempotency key, поэтому сбой между
`send` и commit иногда создаёт дубль.

| `quick_responses` | быстрые ответы, хештеги, авторство, источник, публикация и отложенная валидация |
| `delivery_outbox`, `notification_outbox` | очереди Telegram и webhook |
| `inbound_updates` | дедупликация входящих updates |
| `operator_actions`, `reconciliation_outbox` | аудит Remnawave и очередь сверки |
| `support_blocks`, `blocklist` | блокировки тикетов и совместимость Telegram pre-ticket blocklist |

После успешной обработки сырой Telegram payload удаляется. Метаданные обработанных updates
хранятся 7 дней, завершённые outbox и reconciliation записи — 30 дней; failed-записи
сохраняются для диагностики. История тикетов этим процессом не удаляется.

Схема развивается только Alembic-миграциями и использует PostgreSQL-native типы, включая JSONB.
PostgreSQL разделяет bootstrap, migration и runtime credentials. Provisioning создаёт
least-privilege роли, `postgres-migrate` применяет Alembic, а приложение получает только
`CONNECT`, `USAGE`, DML и необходимые права sequences. Поддержка нескольких экземпляров
приложения отсутствует. Внутри единственного процесса независимые тикеты обрабатываются ограниченно
параллельно: доставка — до 8 заданий, webhook и reconciliation — до 4. Порядок заданий одного
тикета защищён очередями БД; Telegram ingress остаётся последовательным. PostgreSQL engine использует
ограниченный пул: 10 постоянных и до 10 временных соединений.

## Быстрые ответы

При старте приложение создаёт или переименовывает системную Forum-тему `⚡ Быстрые ответы`,
создаёт короткую инструкцию и закрепляет её. ID темы и инструкции хранятся в
`system_settings`. Worker раз в минуту редактированием инструкции проверяет существование темы.
При удалении инструкции создаётся новая; при подтверждённом удалении темы создаётся замена и все
валидные ответы из БД публикуются в ней обычными текстовыми сообщениями.

Авторизованный оператор создаёт ответ обычным `message` в системной теме. Backend извлекает
теги собственным синтаксическим анализатором; семантического анализа, словарей и ML нет. Backend
проверяет каждое использование `#` в сыром тексте: тег должен иметь формат `#текст` без пробела
и содержать букву или цифру. Проверка не зависит от Telegram entities, поэтому цифровые теги вроде
`#1` также поддерживаются. При 0–5 корректных хештегах исходный текст и список тегов записываются
в `quick_responses`. Затем бот публикует одно
каноническое сообщение `исходный текст + два перевода строки + [SAVE]`, фиксирует его ID и
добавляет кнопку мгновенного удаления. Только после успешной публикации бот удаляет исходник
оператора.
Уникальная пара `source_chat_id/source_message_id` делает повторную доставку update и
`edited_message` идемпотентными.

Перед сохранением валидного ответа проверяется длина в единицах UTF-16 с резервом для `[SAVE]`.
При превышении длины, количестве тегов больше пяти или неправильном синтаксисе запись получает состояние
`pending_deletion`, фиксированный `invalid_until` и ID статичного reply-предупреждения.
In-memory задача удаляет исходное сообщение и предупреждение через пять минут; при рестарте задачи
восстанавливаются из БД. Корректный
`edited_message` до дедлайна переводит ту же запись в `valid`, отменяет задачу, публикует
каноническое сообщение и удаляет исходник с предупреждением. Повторные невалидные правки не
продлевают исходный дедлайн.

Поиск и переход к ответу выполняет нативный поиск Telegram по исходному тексту или хештегу.
Кнопка удаления доступна только авторизованным участникам проекта: запись сначала атомарно переводится в
`deleted` с ID оператора и временем, затем удаляется Telegram-сообщение. Если Telegram запрещает
удаление старой публикации, её содержимое заменяется на `🗑 Ответ удалён` без тегов и кнопок.
Сетевые ошибки при удалении или замене сохраняют незавершённую очистку для следующего прохода.
Tombstone остаётся в
БД и не восстанавливается. Если активное сообщение удалили вручную, при следующем запуске бот
обнаруживает отсутствие и публикует его заново.
Inline query handlers, callback-каталог, группы и команды управления ответами отсутствуют.
Startup preflight требует у бота права управления темами и удаления сообщений.
После миграции старые отдельные `[SAVE]` удаляются, а сохранённые ответы приводятся к
каноническому формату один раз; версия формата хранится в `publication_format_version`.

Фоновый проход выбирает только незавершённые публикации: отсутствующий ID, устаревшую версию
формата или оставшееся предупреждение. Кандидаты на публикацию и удаление читаются порциями
по 100 с курсором по ID. Под блокировкой записи состояние повторно проверяется, чтобы удалённый
ответ не был опубликован по устаревшему снимку. Полный проход нужен при запуске и восстановлении
темы; неизменившийся каталог в обычном цикле не вызывает запрос на каждый ответ.

## Авторизация и HTTP API

Telegram-команды требуют активной учётной записи с привязанным Telegram ID и явно выданного
доступа к проекту (либо роли его администратора). Права в самой группе не дают доступа к
приложению. Читать группу позволяют права Telegram, поэтому её членство контролируется отдельно.

Operator API включается отдельно. Все endpoints, включая `/docs` и `/openapi.json`, защищены
`X-API-Token`; общие endpoints принимают любой включённый API token, а пространства `/tickets` и
`/web` — только свой. Мутации дополнительно требуют `X-Idempotency-Key`.
Проверка токена и rate limit выполняются до чтения и JSON-декодирования тела запроса.
Для обычных API endpoints тело ограничено 64 КиБ, включая потоковые запросы без `Content-Length`;
превышение возвращает `413`. Маршрут загрузки `/api/v1/web/messages` сохраняет отдельный лимит
20 МиБ + 64 КиБ на обрамление запроса. Некорректный JSON не обходит учёт запросов и ошибок
авторизации; одна попытка учитывается один раз.
К каждому пути ниже добавляется префикс `/projects/{project_id}`. Токены разных проектов
не взаимозаменяемы; отсутствие project context в PostgreSQL не открывает бизнес-данные.

| Метод | Назначение |
| --- | --- |
| `GET /api/v1/tickets` | список тикетов |
| `GET /api/v1/tickets/{ticket_id}` | тикет |
| `GET /api/v1/tickets/{ticket_id}/messages` | история сообщений |
| `POST /api/v1/tickets/{ticket_id}/messages` | сообщение клиенту |
| `POST /api/v1/tickets/{ticket_id}/close` | закрытие |
| `POST /api/v1/tickets/{ticket_id}/reopen` | повторное открытие |

Точный retry API-мутации воспроизводит сохранённый ответ; другой payload с тем же ключом получает
`409`. Rate limit process-local, forwarded IP принимается только от доверенных proxy. Uvicorn и
Telegram polling находятся в одном процессе, но проектные runtime перезапускаются независимо.

Web API `/api/v1/web` использует независимый token и только server-to-server модель. Identity mode
`external_id` или `email` фиксируется при первом ingress. Мутации idempotent; polling использует
непрозрачный cursor `(created_at, id)`. Фото проверяется по общему размеру запроса, MIME и
сигнатуре, сохраняется в `DATA_DIR/projects/{project_id}/web-media`; подпись ограничена лимитом
Telegram, URL клиента и исходное имя не определяют путь. Ответ оператора Web-клиенту фиксируется в
БД без Telegram delivery job. Для заблокированного тикета входящие сообщения и оценки сохраняются
с `ticket_messages.suppressed=true` и возвращаются в polling как обычные, но исключаются из
Operator API, delivery/lifecycle work и статистики. Исходящие и служебные уведомления подавляются;
точный retry сохраняет исходный скрытый результат. Block/unblock доступны из Forum-темы и через
идемпотентные Web API endpoints; состояние блокировки в клиентский контракт не включается.

## Remnawave

Поддерживается API Remnawave 2.8.x. Telegram ticket ищется по `telegramId`. Web ticket сначала
использует сохранённый UUID, затем точный email lookup; stale UUID очищается. Найденный UUID
сохраняется, но не объединяет Telegram/Web tickets. Перед мутацией выполняется свежий lookup, а
его фактическая identity атомарно обновляется в action и notification intent. Для одного тикета
допускается одна незавершённая мутация.

Действие и reconciliation job фиксируются до внешнего вызова. Timeout, HTTP 5xx, некорректный JSON
или недостоверный success считаются **unknown outcome** и не вызывают повторную мутацию. Worker
только читает состояние и проверяет результат:

- `/gift` — ожидаемую дату окончания;
- `/revokelink` — смену subscription URL;
- `/resetkey` — SHA-256 fingerprint credentials без хранения исходных ключей;
- `/resetdevices` — пустой список HWID-устройств.

Результат сверки: `completed`, `not_applied` или `inconclusive`. Последний блокирует новые
мутации. После независимой проверки администратор может выполнить
`/resolvepanel <action_uuid> applied|not_applied`. Команда не повторяет вызов, использует
first-writer-wins переход и сохраняет решение в аудите. Недоступные read-ответы повторяются с
backoff и после 20 неудач становятся `inconclusive`.

`/revokelink` заранее создаёт durable notification intent. После подтверждения новая ссылка
ставится в webhook-очередь и, по умолчанию, отправляется клиенту в Telegram. Флаг
Проектная настройка `remnawave_revoke_link_telegram_notification=false` отключает только Telegram-сообщение.

## Notification webhook

`notification_outbox` доставляется с семантикой **at-least-once**. HMAC-SHA256 считается от
`<timestamp>.<raw-body>`; получатель обязан проверить подпись и атомарно дедуплицировать эффект
по `event_id` до ответа 2xx. Повторы учитывают тип ошибки и `Retry-After`.

## Наблюдаемость и безопасность

- JSON-логи содержат `event`, trace ID и идентификаторы сущностей;
- Web audit по явному решению владельца содержит email и полный текст сообщений;
- `/projects/{id}/health`, `/ready`, `/metrics` проверяют соответствующий проект;
- Docker healthcheck проверяет heartbeat управляющего цикла установки;
- секреты интеграций должны содержать не менее 32 символов;
- Remnawave/webhook требуют публичный HTTPS; DNS проверяется, соединение закрепляется за
  проверенным IP с сохранением проверки TLS hostname, доступ в локальную сеть запрещён;
- контейнер непривилегированный, root filesystem read-only, capabilities удалены;
- Operator API использует отдельный статический principal каждого проекта;
- multi-instance coordination отсутствует;
- редкий дубль Telegram-сообщения допустим из-за at-least-once.
